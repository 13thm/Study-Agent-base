## 一、它的真实身份
不是"解析聊天记录"，而是 **LLM 应用里 output parsing 的手写版**：输入是不可信的脏文本，
输出必须是下游能 `json.load` 的结构化数据，单条失败不能拖垮整批。
阶段 1 模块 03 的「容错 JSON 解析器」就是它的进阶版。

## 五、我在写这个 Demo 时真踩的两个坑（已修，留着当教材）
| 坑 | 现象 | 根因 | 教训 |
|---|---|---|---|
| except 顺序 | GBK 文件返回退出码 2 而不是 3 | `UnicodeDecodeError` **是** `ValueError` 的子类，先写的 `except ValueError` 把它吃了 | 多个 except 时**子类必须在父类前** |
| split 后不 strip | 正文前带一个空格 | `"a| b"` split 得到 `["a"," b"]` | 分隔符两侧永远要再 strip 一次 |

## 六、练习题
| # | 难度 | 题目 |
|---|---|---|
| 1 | ⭐ | 输出改成 **JSONL**（每行一个 JSON 对象），并说明 JSONL 相比 JSON 数组的优势（流式追加、单行损坏不影响整体、`wc -l` 就是条数） |
| 2 | ⭐ | 加 `--dedup` 参数：同一 user + text 只保留第一条，统计去重了多少 |
| 3 | ⭐⭐ | 加 `--schema` 参数：用 `dataclass` 定义 Record，解析时构造对象而不是裸 dict（为模块 02 的 Pydantic 铺路） |
| 4 | ⭐⭐ | 让它能解析**第二种格式**（`2024-01-05 09:12 张三: 内容`），用策略模式（函数表）而不是 if/elif |
| 5 | ⭐⭐⭐ | 把 12 行样本扩充到 1000 行（用代码生成），测逐行迭代 vs `read().splitlines()` 的内存占用差异（`tracemalloc`） |
